Setup & Running PuzzleScript Next, fortress-rhythm fork

Everything here runs in a browser off a bare checkout — but three things (the editor's EXPORT and SHARE, and the map editor's example loader) need the folder served over HTTP, and a handful of commands only work from the right folder. This page is about getting both right the first time.

The 60-second version

git clone https://github.com/fortress-rhythm/PuzzleScriptNext.git
cd PuzzleScriptNext          <-- the repository root. Almost everything is run from here.
npm start                    <-- leave this terminal open

Then open http://localhost:8020/src/editor.html.

The mistake this page exists to prevent

If the address bar says file:///, you are not running the editor — you are opening it. Writing, running and debugging games works fine that way, which is exactly why it is easy to stay there for months. But the browser blocks a file:// page from fetching other files, so the EXPORT template never loads and every export reports “Can't export yet - still downloading html template.” forever. It is never downloading. It failed at page load.

Worse, the real message is hidden: the fetch fails at startup and prints “Couldn't find standalone template. Is there a connection problem to the internet?”, and then your first Run calls clearConsole() and wipes it. src/js/buildStandalone.js:14-27 · src/js/toolbar.js:14 · src/js/editor.js:244

That is the whole stack. npm install is not part of normal setup — the map editor has no dependencies at all and the Python tools are stdlib-only, so npm start, npm test and the palette checks all run on a fresh clone with nothing installed. You need npm install for exactly one thing: rebuilding the standalone template and the minified bin/.

package.json declares Node 16+ and CI runs Node 22. Anything current is fine. No Node at all? runserver.sh and runserver.bat fall back to python3 -m http.server, which is enough to serve the site (but not to run the checks).

Opening a terminal in the right folder

  • Windows, easiest: open the folder in File Explorer, click the address bar, type powershell (or cmd) and press Enter. The terminal starts in that folder.
  • Windows, typed: cd /d D:\code\PuzzleScriptNext — the /d matters when you are changing drive as well as folder.
  • macOS / Linux: cd ~/code/PuzzleScriptNext.
  • VS Code: open the repository as the folder, and its integrated terminal is already at the root.
Three ways to prove where you are 
git rev-parse --show-toplevel   # prints the root, from anywhere inside the repo
pwd            # macOS / Linux: prints the folder you are in
cd             # Windows cmd, no argument: prints the folder you are in

Or just look: if index.html, package.json and compile.js are all sitting next to each other, you are at the root. ls package.json / dir package.json settles it in one line.

3 Where each command has to be run from

The npm rule, which explains most of the surprises

npm run <script> walks up from your current folder until it finds a package.json, and then runs the script with the working directory set to that package's folder — not to wherever you typed the command. So:

  • You can be in src/ and npm start still works: npm walks up, finds the root package.json, and re-roots itself before running.
  • But this repository contains a second package, puzzlescript-map-editor/, with its own start and test. Stand in that folder and npm finds its manifest first and never looks at the root one.
  • Outside the repository entirely, npm finds nothing (or some unrelated package.json further up) and says Missing script: "start".

Plain commands — node compile.js, uv run tools/… — get no such help. They resolve their paths against the folder you are standing in.

CommandRun it fromWhat happens if you don't
npm start anywhere inside the repo except puzzlescript-map-editor/ From inside that folder you get its start: the map editor alone, on port 8080, with no engine editor served at all. Looks like it worked.
npm test anywhere inside the repo Harmless twin: both manifests run the same map-editor suite.
npm run check:games the repository root The script's argument, src/demo/*.txt, is relative to the root. The pattern itself is safe in any shell: psmap check expands what cmd and PowerShell leave alone.
npm run check:palettes anywhere inside the repo Needs uv on the PATH; the script finds its own data either way.
npm install, npm run build anywhere inside the repo Inside puzzlescript-map-editor/ you would install its (empty) dependencies and find no build script.
node compile.js the repository root, and only there It writes ./bin and ./src/standalone_inlined.txt relative to the current folder. Run elsewhere it either crashes or quietly builds into the wrong place. npm run build is the same thing, re-rooted for you.
uv run tools/palette_test.py the repo root as written Only the path to the script matters — it locates palettes/ from its own location, so a full path works from anywhere.
./runserver.sh, runserver.bat anywhere at all Nothing: both cd to their own folder first, by design.
node puzzlescript-map-editor/src/cli.js check mygame.txt the repo root (the path is relative to you) Adjust the path, or npm link the package and just type psmap.
npm link inside puzzlescript-map-editor/ The one command that belongs in that folder: it puts psmap on your PATH.

4 Serve the checkout

From the repository root, any one of these:

npm start               # node puzzlescript-map-editor/src/serve.js --root . --port 8020
./runserver.sh          # macOS / Linux; node if present, else python3
runserver.bat           # Windows; same fallback
PORT=8081 npm start     # another port (set PORT=8081 first, on Windows cmd)

The server is puzzlescript-map-editor/src/serve.js: about seventy lines, no dependencies, serves the folder given by --root and refuses anything that escapes it. It sends Cache-Control: no-store, so an ordinary reload picks up your edits. Leave it running in its own terminal; Ctrl+C stops it.

PageAddress

Editor — the one you wanthttp://localhost:8020/src/editor.html

Bookmark the editor address, not the file on disk. Port 8020 is deliberate: stock PuzzleScript and PuzzleScript Plus can be served alongside on their own ports.

5 Prove EXPORT actually works

Cheapest check first. Any one of these is conclusive.

  1. Open /src/standalone_inlined.txt directly. You should get roughly 589 KB of HTML beginning <!doctype html> and containing __GAMETITLE__ placeholders. A 404 means the file is missing — go to step 6.
  2. Open DevTools → Network before reloading the editor, then reload. There should be one request for standalone_inlined.txt, status 200. It is fired once at page load and never retried.
  3. Reload the editor and click EXPORT before you Run anything. Because Run clears the console, this is the only moment the startup failure is still readable.

A successful export writes a single self-contained HTML file with your source substituted into the template's __GAMEDAT__ slot. That file is meant to be double-clicked — unlike the editor.

SHARE needs the server too, plus a GitHub account: it uploads the built game as a gist and hands you a link. First use walks you through creating a token.

6 Rebuilding the standalone template

src/standalone_inlined.txt is src/standalone.html with the engine and its stylesheet inlined, and it is committed to the repository, so a fresh clone can export without building anything. But it is a copy: change anything under src/js/ and every game you export still carries the old engine until you rebuild it. That is not hypothetical — the committed template had drifted far enough behind that exported games contained none of this fork's palettes. 

npm run check:export      # is the template current? CI runs this too
npm run build:template    # rebuild it: no npm install, no native binaries

tools/inline_standalone.js behind those two does the one job the big build does for the template, with no dependencies, so it works on machines where compile.js cannot. Run it whenever you touch the engine, and commit the result. The full build does the same thing on its way to the minified bin/ site: 

cd /path/to/PuzzleScriptNext     # the root; compile.js resolves ./src and ./bin from here
npm install                      # once
npm run build                    # = node compile.js

That writes ./src/standalone_inlined.txt (used by the editor you serve) and the minified ./bin/standalone_inlined.txt, alongside the whole optimised bin/ site.

This build is the fragile part of the stack

compile.js pulls in compress-images and gifsicle, which want native binaries and fail on some machines — Windows especially. CI deliberately skips it. Nothing else in the project depends on it, and the committed template means a failed build never costs you the ability to export. If it breaks and you need only the template, the legacy inline.bat does that one job (inliner standalone.html > standalone_inlined.txt) — run it from inside src/, since its paths assume that, and note it wants a global inliner CLI that is not in package.json.

7 The checks to run before you push

npm test                 # map editor suite: parser, bridges, round trip
npm run check:games      # every demo game still opens in the map editor
npm run check:palettes   # = uv run tools/palette_test.py
npm run check:export     # the export template still matches src/js

These four are exactly what .github/workflows/check.yml runs on every push and pull request, on Node 22, with no npm install step. Green locally means green in CI.

The engine's own tests are browser-based and separate: serve the site and open /src/tests/tests.html. To add a case, compile and play in the editor, press Ctrl/Cmd+J, and paste what it prints into src/tests/resources/testdata.js (play sessions) or errormessage_testdata.js (compile errors). See DEVELOPMENT.md.

Troubleshooting

SymptomCause and fix
Can't export yet - still downloading html template. The template fetch failed at page load and will never retry. Nine times in ten you are on file://: serve the folder and use the localhost:8020 address. Otherwise work through step 5.
Couldn't find standalone template. The honest version of the same failure, printed at startup — and erased by your first Run. If you are already served over HTTP, the file is missing: step 6.
npm ERR! Missing script: "start" You are outside the repository, or inside puzzlescript-map-editor/ where check:games and build do not exist. cd to the root.
The server starts, but on 8080, and only the map editor is there Classic: npm start run from inside puzzlescript-map-editor/. That package's start has no --root or --port, so serve.js falls back to its own defaults. Ctrl+C, cd .., start again.
No such file: src/demo/*.txt You are not at the repository root, or you are on a build from before psmap check learned to expand a glob the shell left alone (which is what cmd and PowerShell do, unlike bash). Update, or run it from Git Bash.
EADDRINUSE Port 8020 is taken — often a server you left running in another window. PORT=8081 npm start, or close the other one.
Front page loads, the editor 404s The server is rooted somewhere other than the repository. Check the Serving <path> line it printed on startup.
Your JS edit doesn't show up The server sends no-store, so this is usually the page holding compiled game state, not a cache. Hard-reload with Ctrl+Shift+R.
Tween / LATE warnings on compile Not a setup problem, and no longer a blanket warning: the compiler now names the individual LATE rules that add or remove objects on a layer something can move on, which are the ones that can drop a slide or hand it to the wrong object. A game whose LATE rules only swap objects within a layer, or only touch marker layers, compiles silently.
Tweening does not look like tweening A tween that outlives its turn is cut off, so the gap between turns is the ceiling: keep tween_length below again_interval (0.15s by default) in a game that uses again, and below key_repeat_interval (0.2s) for a held key. Under that, 0.05 is three frames at 60Hz and reads as a jump; around 0.1 reads as movement.
